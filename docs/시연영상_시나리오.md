# 시연 영상 촬영 시나리오

**목표 3분 이내 · 실측 기반 · 컷 편집 없이 실시간 촬영 가능**

구성: Ollama는 호스트에 네이티브 설치(GPU 가속), PostgreSQL만 컨테이너.

---

## 실측 소요 시간

아래는 이 구성에서 실제로 측정한 값입니다. 대본의 타이밍은 여기에 맞춰져 있습니다.

| 구간 | 실측 |
|------|------|
| `docker compose up -d postgres` → `healthy` | 6초 |
| `./mvnw spring-boot:run` → `Started` | 6초 |
| 1번 질문 (모델 콜드 적재 포함) | 8.1초 |
| 2번 질문 `knowledge_graph` | 0.8초 |
| 3번 질문 `nl2sql` | 7.2초 |
| **기계 시간 합계** | **약 28초** |

3분 중 약 152초를 설명에 쓸 수 있습니다. 여유가 있으므로 서두르지 않아도 됩니다.

---

## 촬영 전 준비

**반드시 먼저 할 것**

1. **모든 것을 내린 상태에서 시작** — 기동 장면을 찍어야 하므로
   ```bash
   docker compose down
   ```
   앱이 떠 있으면 종료 (터미널에서 `Ctrl+C`)

2. **네이티브 Ollama는 켜둔 채로** — 이건 영상에서 띄우지 않습니다
   ```bash
   curl http://localhost:11434/api/version
   ```
   응답이 오면 정상

3. **데이터셋이 `dataset/` 에 있는지 확인**

4. **브라우저 탭 미리 열어두기** — `http://localhost:8080` 주소만 입력해 둔 상태
   (앱이 아직 안 떠서 오류가 나지만, 나중에 새로고침만 하면 됨)

5. **화면 정리** — 터미널 글자 크기 키우기(권장 16pt 이상), 불필요한 창 닫기

**녹화 시작**: `Win + Alt + R` (Windows 기본 녹화)

## 타임라인

### 1. 도입 — 터미널 (0:00 ~ 0:15)

> 화면: 프로젝트 디렉터리가 열린 빈 터미널

**말할 내용**

> 2026 오픈소스 개발자대회 지정과제, MCP 기반 지능형 데이터 플랫폼입니다.
> 사용자가 일상어로 질문하면 규칙 기반 라우터가 적합한 도구를 고르고,
> PostgreSQL을 조회한 결과를 로컬 소형 LLM이 문장으로 정리해 답변합니다.
> 외부 API는 전혀 쓰지 않습니다.

---

### 2. 컨테이너 기동 (0:15 ~ 0:30)

**입력할 명령**

```bash
docker compose up -d postgres
```

```bash
docker compose ps
```

**말할 내용** *(명령 실행 중)*

> 먼저 데이터베이스를 올립니다. PostgreSQL에 pgvector 확장을 얹은 컨테이너입니다.
> 컨테이너가 뜨면서 초기화 스크립트가 순서대로 실행돼 스키마와 데이터가 적재됩니다.
> Ollama는 GPU 가속을 위해 호스트에 네이티브로 설치해 두었습니다.

**확인 포인트** — `reaone-postgres`가 `(healthy)`로 표시되는 것을 화면에 잠시 보여줍니다.

> healthy 상태를 확인한 뒤 애플리케이션을 띄웁니다.
> 이 순서를 지키지 않으면 DB 연결에 실패합니다.

---

### 3. 애플리케이션 기동 (0:30 ~ 0:50)

**입력할 명령**

```bash
./mvnw spring-boot:run
```

**말할 내용** *(기동 로그가 흐르는 동안)*

> Spring Boot 애플리케이션이 뜨면서 MCP 서버가 함께 기동됩니다.
> 로그에 `Registered tools: 3`이 보입니다. 과제가 요구하는 도구 세 개가
> MCP 서버에 등록된 것입니다.
> 기동 시 문서 40건의 임베딩과 그래프 데이터 적재도 자동으로 수행됩니다.

**확인 포인트** — `Registered tools: 3` 과 `Started ReaoneProjectApplication` 두 줄을 잠시 보여줍니다.

---

### 4. 시연 ① 문서 검색 (0:50 ~ 1:25)

> 화면 전환: 브라우저 `http://localhost:8080` 새로고침

**말할 내용** *(페이지가 뜬 직후)*

> 화면 상단이 과제가 요구하는 6단계 흐름입니다.
> 질문이 진행되면 단계가 순서대로 밝아집니다.

**조작** — 예시 질문 칩 **`백업 정책은 어떻게 되어 있어?`** 클릭

**말할 내용** *(약 8초 대기 중 — 첫 질문이라 모델 적재 시간 포함)*

> 첫 질문은 모델을 메모리에 올리는 시간이 포함돼 조금 걸립니다.

**결과가 나온 뒤**

> 라우터가 `vector_search`를 선택했습니다.
> 점수를 보시면 9점 대 0점 대 0점입니다.
> "정책", "어떻게", "백업" 같은 문서 키워드가 누적돼 다른 도구를 압도한 결과입니다.
> **이 점수가 곧 판단 근거입니다. 왜 이 도구를 골랐는지 설명할 수 있습니다.**
>
> 답변을 보시면 Product-S1은 매일 2시에 백업하고 26일 보관,
> Product-C4는 90일 보관이라고 나옵니다.
> 문서 40건 중 관련 있는 3건만 추려 그 근거만으로 답을 만든 것입니다.

---

### 5. 시연 ② 관계 탐색 (1:25 ~ 1:50)

**조작** — 칩 **`Client-A가 사용 중인 제품 목록은?`** 클릭 *(약 0.8초 만에 결과)*

**말할 내용**

> 이번에는 `knowledge_graph`가 선택됐습니다. 같은 화면인데 점수 분포가 완전히 다릅니다.
>
> **주목할 부분은 인자입니다.** 라우터가 개체명 `Client-A`와 관계 `USES`를 직접 뽑아냈습니다.
> 도구 이름만 고르는 게 아니라, 호출에 필요한 인자까지 규칙이 만듭니다.
>
> 답변은 Product-C3와 Product-S1.
> PostgreSQL 재귀 CTE로 그래프를 탐색한 결과이며, 1초 안에 끝났습니다.

---

### 6. 시연 ③ 자연어 → SQL (1:50 ~ 2:15)

**조작** — 칩 **`2025년 3분기 총 매출액은 얼마야?`** 클릭 *(약 7초)*

**말할 내용** *(대기 중)*

> 세 번째는 자연어를 SQL로 바꾸는 도구입니다.
> 이 도구만 LLM을 두 번 사용합니다. SQL을 만들 때 한 번, 결과를 문장으로 만들 때 한 번.
> 중간에 데이터베이스 실행이 끼기 때문에 한 번으로 합칠 수 없습니다.

**결과가 나온 뒤 — 원본 근거 펼치기**

> 답은 23,859입니다.
> 아래 **원본 근거를 펼치면 실제로 실행된 SQL이 그대로 들어 있습니다.**
> 답이 맞는지 사람이 검증할 수 있어야 하기 때문에 항상 함께 반환합니다.
>
> LLM이 만든 SQL은 세 겹으로 검증합니다.
> 조회문 외 구문 차단, 읽기 전용 트랜잭션, 실행 시간 제한입니다.

---

### 7. 차별점 (2:15 ~ 2:50)

> 화면: 시연 페이지 그대로 두거나, 결과보고서 표로 전환

**말할 내용**

> 이 프로젝트의 핵심은 규칙과 소형 LLM의 역할을 **측정으로 나눈 것**입니다.
>
> 42개 질문으로 세 방식을 비교했습니다.
> 규칙만 쓰면 38점, LLM에게만 맡기면 34점,
> **둘을 협업시키면 40점**으로 양쪽 단독보다 높았습니다.
>
> 규칙은 도메인 어휘에 강하고, LLM은 표현이 바뀌어도 의미를 잡습니다.
> 그래서 규칙이 확신할 때만 규칙을 쓰고, 확신하지 못하는 질문만 LLM에게 넘깁니다.
>
> 추론 옵션도 작업마다 갈렸습니다.
> SQL 생성은 켜야 정확도가 9할이고, 답변 생성은 끄는 쪽이 세 배 빠르면서
> 오히려 고객사와 제품 이름을 정확히 짚었습니다.

---

### 8. 마무리 (2:50 ~ 3:00)

**말할 내용**

> 응답에는 답변뿐 아니라 선택된 도구, 인자, 라우터 점수, 조회한 원본 근거가 함께 담깁니다.
> 답이 틀렸을 때 라우터, 도구, 모델 중 어디의 문제인지 바로 구분할 수 있습니다.
>
> 모든 모델은 로컬에서 실행되며 데이터는 외부로 나가지 않습니다.
